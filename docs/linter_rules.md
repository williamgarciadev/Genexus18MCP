# GeneXus Linter Rules & Documentation Alignment

## 1. Commit inside Loop (Critical)

- **Concept**: Logical Unit of Work (LUW).
- **Why**: GeneXus manages transactions automatically. Forcing a `Commit` inside a `For each` breaks the cursor and can cause "Cursor not open" errors or severe database locking/contention.
- **Docs**: "It is recommended to incorrectly use the Commit command... effectively ending the LUW."

## 2. Unfiltered Loop (Critical)

- **Concept**: Base Table Navigation.
- **Why**: A `For each` without a `Where` or `Defined by` implies a Full Table Scan of the base table. In large tables (DTOs), this is a performance killer.

## 3. Sleep/Wait (Warning)

- **Concept**: User Experience & Threading.
- **Why**: In Web/Mobile, `Sleep` blocks the IIS thread. If 100 users do this, the server hangs.

## 4. Dynamic Call (Warning)

- **Concept**: Reference Trees.
- **Why**: `Call(&Variable)` prevents GeneXus from knowing the call tree. The object won't appear in "References" and might not be deployed correctly.

## 5. New without When Duplicate (Info)

- **Concept**: Data Integrity.
- **Why**: Inserting a record without handling the `Source` (Example: Unique Index collision) forces a crash. `When duplicate` handles it gracefully.

## Severity policy (normative — mirrors the team standard)

The severities are an operational brake, not decoration. Full standard:
`genexus://kb/skills/clean-architecture` (docs/clean-architecture-genexus.md).

| Severity | Effect |
|---|---|
| **Critical / Error** | Blocks. A task is not done while one is present. |
| **Warning** | Requires a written justification next to the finding: `// GXnnn-justified: <reason>`. |
| **Info** | Logged, does not brake. |

## GX012. Direct Table Access in UI (Warning — raised from Info, 2026-08)

- **Concept**: Separation of concerns (the standard's D — dependency direction).
- **Why**: A `For Each` inside a WebPanel/Transaction event couples the screen to the data
  model and gets copy-pasted into every next screen. UI delegates to a Procedure or Data
  Provider with the canonical signature `parm(in:&Sdt, out:&Result, out:&Messages)`.
- **Suppression**: objects carrying a `PatternInstance` part (WorkWithPlus) are exempt —
  the pattern itself prescribes direct access in its generated Event Start.
- **History**: at Info this was ignored; raised to Warning so it demands a justification.

## GX014. Long Procedure Source (Warning)

- **Concept**: Single Responsibility — the team's size limits.
- **Why**: A main Procedure stays under **80 useful code lines** (non-blank after comment
  stripping; definition in `CodeMetricsExtractor.CountCodeLines`). Beyond that it is doing
  more than one job. Extract: validation ≤60, save ≤50, interop ≤30 lines.
- **Scope**: fires on Procedures only. The other role limits (WebPanel 150, etc.) need
  role inference the linter doesn't have yet — candidates for GX016+ (see debt note).

## GX015. Commented-Out Code Block (Warning)

- **Concept**: Dead code. Version control remembers; the Source should not.
- **Why**: More than 10 consecutive commented-out CODE lines (≥60% of the block looks like
  GeneXus code — prose/change-history comments do not fire). One issue per block.
- **Generated-code exclusion**: regions between DVelop WorkWithPlus markers
  (`/* Generated by DVelop Work With Plus Pattern [Start] - Do not change */` …
  `[End]`, format verified live against a real KB) are skipped — that code is regenerated
  on the next F9 and is not the developer's to delete. `//@ *GENERATED*` banner regions
  (Descartes-style, reported but unverified) are skipped defensively.
- **Detector**: `Helpers/CommentedCodeDetector.cs`, thresholds pinned by
  `CommentedCodeDetectorTests`.
